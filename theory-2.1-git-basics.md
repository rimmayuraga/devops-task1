# Теория для ментора — Task 2.1 (базовая работа с git-репозиториями)

## 1. Принципы децентрализованной системы контроля версий Git

Git — **распределённая** VCS: у каждого разработчика есть **полная копия** репозитория
со всей историей. Работать можно офлайн; синхронизация — обменом коммитами между
репозиториями (push/pull). Нет единого «главного» сервера, без которого нельзя работать.

## 2. Как Git хранит версии файлов и историю

Git хранит **снимки (snapshots)** всего дерева файлов на каждый коммит, а не разницы.
Неизменённые файлы не дублируются — на них просто ссылаются (экономия места).
Каждый коммит ссылается на предыдущий — получается цепочка истории.

## 3. Внутренняя структура репозитория

- **Объекты** (`.git/objects`): blob (содержимое файла), tree (каталог), commit (коммит),
  tag. Адресуются по SHA-1/SHA-256 хэшу.
- **Индекс** (`.git/index`): «зона подготовки» (staging) — что попадёт в следующий коммит.
- **Ссылки** (`.git/refs`, `HEAD`): ветки и указатель на текущий коммит.
- **Журналы**: `reflog` — история перемещений HEAD.

## 4. Отличия GitHub, GitLab, Bitbucket

| | GitHub | GitLab | Bitbucket |
|---|---|---|---|
| Владелец | Microsoft | GitLab Inc. | Atlassian |
| CI/CD | GitHub Actions | GitLab CI (встроен) | Pipelines |
| Особенность | крупнейший, соц. функции | можно ставить on-premise | тесная интеграция с Jira |

## 5. Дополнительные функции

- **GitHub**: Actions, Packages, Codespaces, Issues, Projects.
- **GitLab**: встроенный CI/CD, registry, wiki, self-hosted, DevOps-полный цикл.
- **Bitbucket**: интеграция с Jira/Confluence, Pipelines.

## 6. Как выбрать хостинг

- Нужен **self-hosted** и полный DevOps → GitLab.
- Открытые проекты, сообщество, Actions → GitHub.
- Команда на **Atlassian (Jira)** → Bitbucket.

## 7. Рекомендации по коммит-сообщениям

- Короткая **первая строка** (до ~50 символов), затем пустая строка и подробности.
- **Повелительное наклонение**: «Add», «Fix», «Update».
- Один коммит — одна логическая правка.

## 8. Конвенция «тип: описание» (Conventional Commits)

Формат: `<тип>: <описание>`, например `feat: Add new feature`.
Типы: `feat` (новая функция), `fix` (исправление), `docs`, `style`, `refactor`,
`test`, `chore`. Пример: `fix: Correct worker_connections value`.

## 9. Как разделять изменения на коммиты

Каждый коммит — **одно логически цельное изменение**. Не смешивать несвязанные правки.
Пример: отдельно «Add README» и «Add default nginx.conf», как в этой задаче.
Так история читаема, а откат/ревью точечные.
